# Smart Perimeter

ブループリントで構築されたHome Assistant用の警報・防犯システムです。一般的な自作アラームにはない2つの特徴があります。

1. **複数人対応のアーム/ディスアーム。** 「誰が認証したか」を数値IDで返すセンサー(指紋認証リーダー、キーパッド、NFCリーダーなど)から動作し、アーム状態の管理は単一の情報源(single source of truth)に一元化されています。どのデバイス・どの人が操作しても、状態がずれることはありません。
2. **ペットを考慮した部分モード。** 留守番中のペットがいる場合、通常のアラームのモーションセンサーはペットの動きに反応して誤報を出し続けます。本システムはカメラのAI物体検出([Frigate](https://frigate.video/)の"dog"オブジェクトトラッキングでテスト済みですが、カメラごとに「ペットが映っている」というバイナリセンサーを返すインテグレーションであれば何でも使えます)を利用し、誰も(人もペットも)家にいないときは自動で**フル**モード(全センサー有効)、ペットだけが留守番しているときは**パーシャル**モード(ドア/窓のみ、室内モーションは無視)でアームします。

すべて[Home Assistant ブループリント](https://www.home-assistant.io/docs/automation/using_blueprints/)としてパッケージ化されています。インポートして自分のエンティティを入力するだけ、基本セットアップにYAMLの手直しは不要です。

## 普通のアラームインテグレーションではダメなのか?

もちろん使って構いませんし、ドアやサイレンといった基本部分は既にお使いのアラームパネルのインテグレーションを流用すべきです。本プロジェクトは、ほとんどのアラームが抱える特定の弱点を埋めるために存在します。それは**ペットと侵入者を区別できない**という点です。そのため、室内モーションセンサーを常時無効にする(セキュリティが弱くなる)か、ペットが動くたびに誤報と付き合うかのどちらかになってしまいます。

## このリポジトリのブループリント

| ブループリント | ドメイン | 役割 |
|---|---|---|
| `arm.yaml` | script | システムをアームする。特に指定がなければペット用センサーからフル/パーシャルを自動判定 |
| `disarm.yaml` | script | ディスアームする。実際にサイレンが鳴っていた場合はその副作用を元に戻す |
| `person_trigger.yaml` | automation | 1人につき1インスタンス。数値IDセンサーからアーム/ディスアームを切り替える |
| `perimeter_trigger.yaml` | automation | 侵入検知でサイレンを鳴らす。モードを考慮する |
| `rearm.yaml` | automation | センサーが待機状態に戻ったらサイレンを解除する |
| `auto_arm_away.yaml` | automation | 在宅トラッカーが全員外出中と示したら自動でアームする |
| `pet_false_alarm_guard.yaml` | automation | ペットが原因の誤報を自動修正し、必ず通知する |

実際に重要なハードウェア(カメラ/GPU、認証デバイス、サイレン、音声サテライト、外出先での確実な在宅検知のためのVPN)については [`docs/hardware.md`](../hardware.ja.md) を参照してください。

## 前提条件

- 人ごとに数値IDで認証する手段(一致したIDを`sensor.*`として公開するZigbee/Tuya指紋認証リーダーが、本プロジェクトの構築時に使用したリファレンス実装です。番号にマッピングされたコードを使うキーパッドや、NFCリーダーでも同様に動作します)。
- サイレンの`switch.*`エンティティ。
- 「アーム状態」用の`input_boolean`。
- 「パーシャルモード」フラグ用の2つ目のブール型相当のエンティティ。理想的には2つ目の`input_boolean`ですが、**もし**お使いの環境で自動化ツールから新しいヘルパーエンティティを作成できない場合(私たちのケースがそうでした。Home AssistantのREST設定APIはオートメーションやスクリプトの作成・編集には対応していますが、`input_boolean`/`input_select`ヘルパーの作成には対応していません)、on/off状態のためだけに余っている`automation`エンティティを代用できます。多少の裏技ですが問題なく動作し、エンドユーザーからは見えません。`blueprints/script/ha-smart-perimeter/arm.yaml`で、`homeassistant.turn_on`/`turn_off`を使って汎用的にon/offを扱う方法を確認してください。どちらの種類のエンティティでも動作します。
- (ペット対応モード用、任意)カメラごとに「ペット検出」バイナリセンサーを返すカメラAIパイプライン。Frigateの場合、カメラ設定の`objects.track`に`dog`(または飼っている動物種)を追加するだけです。カスタムモデルの学習は不要で、`dog`はFrigateの検出モデルの多くがサポートする標準COCOの80クラスの1つです。
- (外出時自動アーム用、任意)信頼できる`person.*`/`device_tracker.*`の在宅状況。Wi-Fiネットワークを出た際にこれが実際に機能するためには、VPN/リモートアクセスが前提条件になることについて`auto_arm_away.yaml`内の注記を参照してください。

## インストール

1. Home Assistantで: 設定 → オートメーションとシーン → ブループリント → ブループリントをインポート、このリポジトリ内の各`.yaml`ファイルのGitHub raw URLを貼り付けます(または、ファイルを`config/blueprints/...`のフォルダ構成にコピーしてリロードするだけでも構いません)。
2. アーム状態用の`input_boolean`(理想的にはパーシャルモード用の2つ目も)を、設定 → デバイスとサービス → ヘルパー で作成します。
3. `arm.yaml`からスクリプトを1つ、`disarm.yaml`からもう1つ作成し、自分のエンティティを入力します。
4. アーム/ディスアームできる**人ごとに1つ**、`person_trigger.yaml`オートメーションを作成します。
5. `perimeter_trigger.yaml`、`rearm.yaml`、`pet_false_alarm_guard.yaml`からオートメーションを作成します。**最初は無効のままにしておいてください** — アームスクリプトがこれらを自動でオン/オフします。アームされたセッションの外で独立して有効化すべきではありません。
6. 任意で、全員が外出したときに手を触れずにアームする`auto_arm_away.yaml`を追加します。

## 学んだこと(実際のセキュリティ用途で頼る前に読んでください)

- **瞬間的な在室チェックは脆弱です。** 最初のバージョンはアームする「まさにその瞬間」に「今ペットが見えているか」をチェックしており、しばしば誤判定していました — ペットがたまたま1分ほどフレームの外にいただけでも失敗します。`arm.yaml`スクリプトは代わりに**時間の幅**(デフォルトでは直近15分以内にペットが見られたか)をチェックするようにしており、はるかに許容範囲が広くなっています。`pet_false_alarm_guard.yaml`オートメーションはあえて逆(瞬間的なチェック)を行います。そこで問うべき質問が違うからです。「今この瞬間、この特定のトリガーの原因はペットか?」という問いです。
- **カメラベースの「誰か家にいるか」は、スマートフォンベースの在宅状況とは違います。** カメラはレンズが向いている部屋しかカバーしません。当初は「どのカメラにも人が映っていない」を自動アームのトリガーに使っていましたが、家族がまだ家の中にいる(カメラが映していない部屋にいただけ)のに家をアームしてしまうという、実際に起きたリアルな誤報につながりました。`auto_arm_away.yaml`はこれを避けるために、特に`person`/`device_tracker`の在宅状況を軸に構築されています。ここをカメラの在室センサーに差し替えないでください。
- **独立した2つのアーム/ディスアーム入力デバイスには、単一の情報源が必要です。** アームする方法が複数ある場合(例:指紋認証リーダー*と*キーフォブリモコン)、デバイスごとに別々のロジックを書くのではなく、両方とも同じアーム/ディスアームスクリプトを経由させてください。そうしないと、「アーム済み」ヘルパーと実際のシステム状態が気づかないうちにずれてしまう可能性があります。
- **「ペットが本当に出て行ったか」を定期的にバックグラウンドでチェックするのは、実質的なトレードオフであり、無料のアップグレードではありません。** しばらくペットが見られなければパーシャルからフルへ自動的に格上げする定期的な再チェックの追加を検討しましたが、あえてデフォルトの挙動としては含めていません。これは元のバグの原因となったのと全く同じ「カメラが見えているか」という脆弱な信号を、逆方向に使うだけだからです。もし自分で追加する場合は、アーム時のチェックよりも明らかに広い「確実にいなくなった」ウィンドウ(15分ではなく30〜40分を推奨)を使ってください。パーシャルからフルへの誤った格上げは誤報を再発させますが、パーシャルに少し長くとどまることのコストはモーションカバレッジの低下だけで済むからです。
